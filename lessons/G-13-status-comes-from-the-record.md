# G-13 · Status comes from the record, never from your last report

**Read status out of the per-application records, mechanically, before writing any list of
what to do next.** Never from memory, and never from yesterday's summary, because yesterday's
summary was also written from memory.

## Why summaries rot

A summary is correct on the day it is written. Then something changes and the summary does
not. **Copying it forward makes yesterday's snapshot look like today's state**, and the error
compounds silently: each copy inherits every stale entry and adds a fresh one.

## Make it a step, not an intention

A rule that lives as a sentence gets broken. A rule that produces output gets followed.

*As a sentence:* "always check the current status first". Broken within a week.

*As a step:* "run the status extraction over every application record, paste the output, and
build the list from that output." **This one cannot be skipped without the gap being visible**,
because the output is either there or it is not.

## Two dates every item carries

**Every finished package gets a send-by date.** A package that is ready and unsent is not
progress. It is a deadline quietly approaching.

**Every drafted message gets a send-by date too.** A draft written for a moment goes stale
when the moment passes; a note about an application is worth much less three weeks later.

## Write the decision down the same day

**A decision that lives only in a conversation is lost.** Decided not to apply, decided to
wait, sent it, heard back: it goes into the record the same day, or the record starts lying.
